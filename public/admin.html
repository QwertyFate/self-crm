Using the provisioning API

One request creates a customer workspace, its owner account, any custom fields it should start with, and a working inbound webhook — and hands back the owner's password and the webhook URL to send on. The Provisioning tab is a form over exactly this API. Every snippet below already uses this console's host; copy and run.

1 · Authenticate: the admin secret goes in the payload

No login step. Put admin_secret (the server's ADMIN_SECRET) in the JSON of the request itself — one request does everything. For GET requests send it as the X-Admin-Secret header instead. The secret is checked in constant time and dropped before the request is processed; it never appears in a response. Treat it like a password: HTTPS only, never in a URL.

The console's own way still works too — POST /api/admin/login once and reuse the session cookie:

curl -c cookies.txt -X POST https://YOUR-HOST/api/admin/login \
  -H 'Content-Type: application/json' \
  -d '{"secret":"YOUR_ADMIN_SECRET"}'
# then add  -b cookies.txt  to the requests below and leave admin_secret out

2 · Provision — the smallest request

POST /api/admin/provision — the secret plus the workspace name and the owner's email. Nothing else is required.

curl -X POST https://YOUR-HOST/api/admin/provision \
  -H 'Content-Type: application/json' \
  -d '{
    "admin_secret": "YOUR_ADMIN_SECRET",
    "workspace_name": "Acme Corp",
    "owner_email": "maria@acmecorp.com"
  }'

3 · A full request

Everything the endpoint accepts. Custom fields apply to this new workspace only; afterwards its own members manage them in Settings.

{
  "admin_secret":   "YOUR_ADMIN_SECRET",      // required (unless you sent the session cookie)
  "workspace_name": "Acme Corp",              // required
  "owner_email":    "maria@acmecorp.com",     // required
  "owner_name":     "Maria Schmidt",          // optional — defaults to the part before the @

  "contact_fields": [                         // optional — extra fields on every contact
    { "name": "Lead Source", "type": "dropdown", "options": ["Google Ads", "Referral"] },
    { "name": "LinkedIn",    "type": "url" }
  ],

  "deal_fields": [                            // optional — extra fields on every deal
    { "name": "Contract Start", "type": "date" },
    { "name": "Seats", "field_key": "seat_count", "type": "number" }
  ],

  "create_deal":    true,                     // optional, default true — inbound leads also open a deal
  "webhook_active": true                      // optional, default true
}

5 · The list

GET /api/admin/provision/list — every workspace with its owner, newest first; provisioned_at is set only for workspaces created through this API.

curl -H 'X-Admin-Secret: YOUR_ADMIN_SECRET' https://YOUR-HOST/api/admin/provision/list

Custom fields

Each entry in contact_fields / deal_fields takes:

KeyRequiredNotes
nameyesWhat the user sees, e.g. "Lead Source"
typenoDefaults to text. One of text, email, phone, number, dropdown, date, url
optionsonly for dropdownA dropdown with no options is rejected
field_keynoAuto-generated from name ("Lead Source" → lead_source). Set it if you need a specific key
  • Up to 50 fields per object. A contact field key may not collide with a built-in column (name, email, phone, company, assigned_to, …) — that is a 400.
  • Contact fields are wired into the webhook automatically: each one is added to field_map, so the customer can send lead_source in their payload and it lands on the contact.
  • Deal fields are not fillable by the webhook. They work on the deal board and in the deal modal, but an auto-created deal gets a title, pipeline and stage only. This is repeated in integration.notes of every response.
  • Fields can only be seeded here, at creation. The API cannot add fields to an existing workspace — once it is live, its owner/admins manage fields in Settings → Custom fields.

The owner's password

  • Generated per workspace: 16 characters in four groups, e.g. Z5ri-jBxY-cQ3V-QJgV; look-alike characters (0/O, 1/l/I) are excluded so it survives being retyped.
  • Shown once, in the response. Not stored, not emailed. Only a bcrypt hash is kept — nobody can read it back later. Copy it before closing the response.
  • Lost? The owner uses Forgot password on the login page and sets their own. Suggest they do that anyway, since you have seen the first one.
  • If the email already has an account, the owner keeps their existing password and existing_account is true — no new credentials. One person can own several workspaces with one password; at login they are asked which workspace to open.

Handing over the integration

Give the customer integration.webhook_url and integration.sample_curl. The webhook takes a POST with JSON and needs no header or token — the key in the URL is the secret, so treat the URL itself as a credential.

  1. The payload is mapped through field_map (nested paths work: "data.contact.email").
  2. At least a name or an email is required, otherwise 422.
  3. An existing contact is matched and updated by email; with no email a new one is always created.
  4. Anything mapped that is not name/email/phone/company is stored on the contact as a custom field.
  5. A deal is opened in the first pipeline stage, if create_deal was on.
  6. The delivery is logged either way.

Rate limits: 120 requests per minute per key, 120 per 15 minutes per IP. The owner can change the mapping, rotate the key or switch the webhook off under Settings → Integrations, where the last 50 deliveries are listed — the first place to look when "my form isn't coming through".

Errors

Every failure is { "error": "…" } with a message meant to be read. Nothing is half-created: the whole thing runs in one database transaction.

StatusMeans
400Something in the request is wrong — the message names the field, e.g. contact_fields[1].type "money" is not valid
401admin_secret (or the X-Admin-Secret header) missing or wrong, and no admin session
503ADMIN_SECRET is not configured on the server — the admin API is off
  • Workspace names are not unique. Provisioning twice with the same name gives two separate workspaces — check the list first.
  • It can only create. A stray workspace_id in the body is ignored; there is no way to point it at an existing workspace.
  • APP_URL must be set on the server, or the generated login and webhook URLs point at the wrong host.
  • Nothing is emailed — not the password, not the webhook URL. Handing them over is a manual step, by design.

The Upgrads Engine API

The Onboarding Engine is a separate service. The CRM tells it what happened (signed webhooks: a new customer, changed master data, a signed contract, an uploaded document) and the Engine reads and writes the customer through a REST API under /api/kunden/…, authenticated with a per-workspace API key. This page walks through both halves with runnable requests against this host. The full machine-readable description is the OpenAPI 3.1 document: GET /api/kunden/openapi.json with a key, or the download link on the workspace's API keys card.

Keys are per workspace and are not created here. A workspace owner or admin creates them under Integrations → Upgrads Engine → API keys; this console has no access to a workspace's data by design.

1 · Set a workspace up for the Engine

  1. Integrations → Upgrads Engine: enter the Engine URL (public host; private addresses are refused), tick the trigger stages that mean "contract signed" (preselected from the Analytics won stages), copy the webhook secret, click Send test event, switch to Active.
  2. API keys card: create a key named after its user (e.g. "Engine production"). It is shown once; the CRM keeps only its hash. Revoking cuts the Engine off at once.
  3. Download the OpenAPI document from the same card. Hand the Engine team the key, the webhook secret, the document and ENGINE_INTEGRATION.md.
  4. The Onboarding page (sidebar, owners/admins, visible while the integration is active) lists every deal with the Engine's status, the Drive folder link, the last webhook result and a Start onboarding button that moves a deal into the trigger stage.

Server side, three settings matter: BASE_URL (the public origin that goes into download_url values), a private Supabase bucket contact-documents (or SUPABASE_DOCS_BUCKET) for contracts and recordings, and ENGINE_RETRY_WORKER=0 on any second instance that must not re-drive webhooks.

2 · Authenticate and read a customer

Authorization: Bearer <key> (or X-API-Key) on every call. kunde_id is the CRM contact id — the same number the webhooks carry. A customer of another workspace answers 404, never 403; every authentication failure is the same 401.

3 · Set the onboarding status (and the Drive linkage)

Every write needs an Idempotency-Key: the same key with the same body within 24 h replays the stored answer (Idempotent-Replayed: true); the same key with a different body is 422. drive_ordner_id and akte_version are optional and touched only when present. A status change never triggers a webhook, so the two systems cannot loop.

curl -X PATCH https://YOUR-HOST/api/kunden/42/status \
  -H 'Authorization: Bearer upg_live_YOUR_KEY' \
  -H 'Idempotency-Key: 6b2f0c3e-status-1' \
  -H 'Content-Type: application/json' \
  -d '{ "onboarding_status": "termin_gebucht", "drive_ordner_id": "1AbC…", "akte_version": 3 }'
StatusMeaning
kein_onboardingDefault; no contract yet

4 · Add master data — empty fields only

PATCH /api/kunden/42 never overwrites a populated field. A populated field with a different value is reported in konflikte and written as a note on the customer (signed "Upgrads Engine") instead; equal values are ignored; null and "" mean "nothing to add". Send akte_version as the version you last read and a stale one is 409 — re-read and decide again. Unknown keys are 422.

curl -X PATCH https://YOUR-HOST/api/kunden/42 \
  -H 'Authorization: Bearer upg_live_YOUR_KEY' \
  -H 'Idempotency-Key: 6b2f0c3e-stammdaten-1' \
  -H 'Content-Type: application/json' \
  -d '{
    "rechtsform": "GmbH",
    "handelsregisternummer": "HRB 12345",
    "webseite": "https://muster-immobilien.de",
    "adresse": { "strasse": "Musterstraße 1", "plz": "01067", "ort": "Dresden" },
    "akte_version": 3
  }'
{

5 · Documents: contracts and recordings

The team uploads files on the contact's Documents tab (types vertrag, aufnahme, sonstiges; 10 MB each). The Engine lists them and fetches the bytes through the CRM — the storage is private and every download is a 302 to a link that lives ten minutes.

curl -H 'Authorization: Bearer upg_live_YOUR_KEY' \
  https://YOUR-HOST/api/kunden/42/dokumente

#                      "groesse": 184233, "erstellt_am": "…", "download_url": "https://YOUR-HOST/api/dokumente/9/download" } ] }

curl -L -o vertrag.pdf -H 'Authorization: Bearer upg_live_YOUR_KEY' \

6 · Notes and communication

GET /api/kunden/42/notizen returns the team's notes and call logs (typ notiz/anruf, plain-text inhalt, quelle crm/engine); filters typ, seit, limit. The Engine logs its own results with a POST — the note appears on the customer signed "Upgrads Engine". GET /api/kunden/42/kommunikation returns hand-logged e-mails and WhatsApp messages: the CRM has no mailbox, so betreff, richtung and absender are null and every answer says so in hinweis.

curl -X POST https://YOUR-HOST/api/kunden/42/notizen \
  -H 'Authorization: Bearer upg_live_YOUR_KEY' \
  -H 'Idempotency-Key: 6b2f0c3e-notiz-1' \
  -H 'Content-Type: application/json' \
  -d '{ "inhalt": "Onboarding-Call ausgewertet.\nOffene Fragen: 3 (siehe offene-fragen.md)", "vertrag_id": 17 }'
# → 201 { "id": 901, "typ": "notiz", "inhalt": "…", "quelle": "engine", "autor": "Upgrads Engine", "vertrag_id": 17, … }

Verifying on the Engine side (Node.js; keep the raw body — re-serialising the parsed JSON breaks the signature):

const crypto = require('crypto');

function verify(secret, req, rawBody) {          // rawBody: Buffer or string of the exact request body
  const sig = String(req.headers['x-upgrads-signature'] || '').trim().toLowerCase();
  const expected = crypto.createHmac('sha256', secret).update(rawBody).digest('hex');
  const a = Buffer.from(expected), b = Buffer.from(sig);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
  • Answer any 2xx quickly and do the work asynchronously. Any other 4xx (401, 404, 422, …) is treated as a configuration error and not retried; redirects are not followed.
  • Retries on network errors, timeouts (10 s), 5xx, 408 and 429: 7 attempts — immediately, then +1 min, +5 min, +30 min, +2 h, +6 h, +16 h (≈ 24.6 h). They are stored in the database and driven by a worker, so they survive a CRM restart; the current secret and URL from the card apply to each retry.
  • The workspace's Integrations → Deliveries list shows every event with its attempts and the last response; owners can Retry a failed one by hand. Switching the integration off pauses pending retries; switching it on resumes them.

Errors, limits, ids

Every failure is { "fehler": { "code", "nachricht" } } (German message) with a meaningful status — never HTTP 200 with an error body; unknown paths under /api/kunden and /api/dokumente are a JSON 404, not the web app.

StatusCodes
400ungueltige_id, idempotency_key_fehlt, idempotency_key_ungueltig
401nicht_authentifiziert — missing, malformed, unknown, revoked or expired key (always the same answer)
404nicht_gefunden — not in this key's workspace, or an unknown path
409akte_version_konflikt (stale precondition), anfrage_in_bearbeitung (same key still running)
422ungueltige_daten, ungueltiger_status, keine_daten, idempotency_key_konflikt
429zu_viele_anfragen — 300 requests per minute per IP across /api/kunden and /api/dokumente
500serverfehler — no internals are disclosed
  • Ids are integers: kunde_id = contact id, vertrag_id = deal id, document and note ids likewise. Timestamps are ISO 8601 in UTC.
  • The Akte (the ~60-field record) lives in Google Drive, not in the CRM — the CRM keeps master data, the status, drive_ordner_id and akte_version only.
  • Keys expire only when revoked; scopes are stored but not enforced — every key may call every endpoint of its workspace.
  • Open with the Engine team: plain-hex signature vs. sha256= prefix, integer vs. string ids, the akte_version model. The contract document (ENGINE_INTEGRATION.md) states what is built.
